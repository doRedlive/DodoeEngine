# ScriptPanel 脚本工作区调研与改造建议

日期：2026-11-11  
状态：调研与方案，待实施  
依据：当前工作区源码（含本地改动，HEAD 为 `9b585dcd`）及文末官方资料。

## 1. 要解决的核心问题

**打开 ScriptPanel，就应自动进入当前项目的脚本工作区：识别整个 Assets 下的全部 C# 脚本，按真实目录结构展示，直接浏览、搜索和编辑。** 用户不应该先去 Project 面板逐个双击脚本，才能在这里看到内容。

目标体验以“VS Code 打开 Unity 项目”为参照：左侧是项目文件目录，中间是多标签代码编辑区，当前文件的大纲是辅助视图。字体、括号与引号自动闭合、补全、诊断和修改后的生效机制，服务于这个完整工作区。

建议的优先顺序：

1. **先把工作区做出来**：自动绑定项目、完整扫描 Assets、目录树、文件切换、外部变更同步。
2. **再把编辑和项目理解接上**：可靠保存、常用快捷键、字号、自动闭合、跨文件搜索与 C# 语言服务。
3. **最后完善修改后的生效闭环**：诊断、后台编译、受控重载和 Play 前版本检查。

首版完成标准：**即使一个文件都没打开，ScriptPanel 也必须显示当前项目的 Assets 脚本目录树。关闭最后一个标签后，目录树仍然存在。**

## 2. 当前实现与目标的具体差距

下表描述源码中可确认的行为；体验和性能判断属于静态分析，尚不是实际运行测量。

| 方面 | 当前实现 | 与目标的差距 |
|---|---|---|
| 打开入口 | Project 面板发出 `scriptOpenRequested`，外壳展开 Script Dock，再调用 `openFile` | 主要流程围绕单个文件打开，没有独立完整的脚本工作区入口逻辑 |
| 左侧树 | `m_outline` 展示当前文件的 namespace、class、method 等符号 | 这是文件大纲，不是 Assets 文件目录树 |
| 无打开文件 | `m_pages` 为空时，`QStackedWidget` 显示“到 Project 双击 .cs”提示 | 整个包含左侧栏的 splitter 被隐藏，工作区无法独立浏览 |
| 脚本发现 | `CSharpSymbolIndex::rebuild` 已递归扫描资产根目录下的 `.cs`；首次打开文件或 `reopenProject` 可触发 | 已有扫描基础，但只供符号索引使用，没有输出为项目文件树 |
| 扫描覆盖 | 符号索引按目录名跳过 `Build`、`packages`、`Temp` 等；Project 树另有过滤规则 | 不能直接把这些结果当作“Assets 全部脚本”的权威清单 |
| 外部变化 | ScriptPanel 的 watcher 为已打开文件添加监听 | 未打开文件的新增、删除、移动缺少工作区级维护 |
| 项目树复用 | ProjectViewModel 已有递归目录模型；ProjectPanel 已有目录监听和文件操作入口 | 可以复用底层能力，但现有树混合多种资产，且扫描/重建主要同步进行 |
| C# 项目理解 | `QCompleter` 使用词条；定义跳转主要按符号名查找 | 缺少类型、作用域、程序集引用和未保存缓冲区的语义理解 |
| 编辑体验 | 行号、高亮、多标签、查找替换、基础缩进、F12/返回已有；字体设置为 Consolas 11pt | 缺少字号配置入口、成对输入及更完整的代码操作 |
| 保存与生效 | `savePage` 写文件后更新大纲/符号索引 | 没有连接到 Qt 脚本工作区中的编译、诊断和重载闭环 |

证据入口：E1—E5、E8。需要准确区分：**现在并非完全不会扫描脚本，而是扫描结果没有形成以项目为单位、持续同步的脚本工作区。**

## 3. 打开 ScriptPanel 后应当发生什么

### 3.1 默认打开流程

1. 从当前 `EditorSession::assetRoot()` 取得资产根目录。不要硬编码仓库路径，也不要固定到 `Assets/Scripts`。
2. 立即显示工作区外壳：项目名称、Assets 根节点、搜索框、编辑区和状态栏。
3. 自动扫描 Assets 全部层级中的 `.cs` 文件，异步建立目录快照；扫描过程中显示“正在读取脚本目录”。
4. 分批显示目录和文件。即使语义服务尚未准备好，也能浏览和打开文件。
5. 注册目录变化监听，接收内部资产操作事件，并同步新增、删除和重命名。
6. 按项目恢复上次展开的目录、打开的标签及光标位置；没有历史记录时，编辑区显示欢迎提示，目录树正常保留。
7. 在后台准备该项目的 C# 工程上下文与索引；完成后再启用语义跳转、成员补全和诊断。

首次显示面板、切换项目、重新显示已隐藏面板，都应走同一个幂等的工作区入口。再次显示时进行增量校验，不应每次销毁所有标签再全量扫描。

现有 `AssetController::projectRoot()` 实际返回 `m_session.assetRoot()`。接入时注意这个命名，避免误将仓库根目录当作脚本根目录。[E5]

### 3.2 目录树示例

下面是目标结构示意，文件名不代表当前项目的实际内容：

```text
当前项目
└─ Assets
   ├─ Scripts
   │  ├─ Gameplay
   │  │  ├─ PlayerController.cs
   │  │  └─ EnemyController.cs
   │  └─ Shared
   │     └─ GameState.cs
   ├─ Editor
   │  └─ SceneTools.cs
   ├─ Plugins
   │  └─ Helpers
   │     └─ MathHelper.cs
   └─ Bootstrap.cs
```

关键要求：

- `Assets/Bootstrap.cs`、任意嵌套目录下的脚本，都能被发现，不能只扫描名为 Scripts 的文件夹。
- 目录节点保留真实父子层级；文件夹优先，再按名称排序；同名文件通过相对路径区分。
- 默认显示全部实际目录，包括空目录，方便在其中新建脚本；文件层仅显示 `.cs`，不显示 `.meta`。后续可提供“隐藏无脚本目录”选项。
- 默认不因为目录叫 `Build`、`Configs` 或 `packages` 就静默隐藏其中的合法脚本。忽略规则必须显式定义，并统一应用到发现、索引和工程清单。
- 文件系统是发现文件的依据，资产数据库补充 GUID 等信息；尚未导入数据库的新 `.cs` 也应先出现在目录树中。
- 根目录是当前项目资产根，而不是整个磁盘。符号链接/junction 默认不跨出根目录，防止重复遍历和循环；被跳过的路径应能说明原因。

首期只承诺 `.cs` 工作区；其他脚本语言应按文件类型显式接入，不能混用 C# 的补全、诊断与执行规则。

### 3.3 面板布局与操作

| 区域 | 主要内容 | 行为 |
|---|---|---|
| 左侧上部 | Explorer：Assets 文件目录树、过滤框、刷新、折叠全部 | 默认常驻，不受打开标签数量影响 |
| 左侧下部 | Outline：当前文件的符号大纲 | 可折叠，保留现有大纲功能 |
| 中间 | 多标签代码编辑器、当前文件路径 | 切换标签联动树选中项；同一路径只开一个文档 |
| 下部 | Problems 与脚本输出 | 错误按文件归组，双击跳到行列 |
| 状态栏 | 项目、索引状态、行列、保存状态、生效状态 | 区分“已保存”“待编译”“待应用”“已生效” |

建议分两步提供文件操作：

- 首版：单击选中，双击/Enter 打开；文件名过滤、相对路径显示、定位当前文件、刷新；关闭最后一个标签保留目录。
- 后续：新建脚本/文件夹、重命名、删除、移动、右键在 Project 中定位，以及 Ctrl+P 快速打开。目录移动必须同步更新所有子文件路径。

单击预览标签、双击固定标签可以后续补齐；首版优先保证文件目录、文档和保存状态一致。

### 3.4 各类空状态应分别处理

| 情况 | 应显示的内容 |
|---|---|
| 未打开项目 | “打开项目以浏览脚本”，不显示上一个项目的目录 |
| 项目存在但没有脚本 | Assets 目录结构与“暂无 C# 脚本”，提供新建入口 |
| 没有打开文件 | 完整目录树；编辑区提示“从左侧选择脚本” |
| 目录不存在或无权限 | 保留项目身份，显示具体目录问题和重试入口，不能假装扫描成功 |
| 语言服务未就绪/不可用 | 正常浏览、打开、编辑；状态栏提示语义功能尚不可用 |

## 4. 应建立的三个模型

完整工作区需要区分以下数据，避免继续让 `m_pages` 同时承担所有职责。

| 模型 | 表达什么 | 不能混淆的边界 |
|---|---|---|
| 脚本目录清单 | 当前 Assets 中有哪些脚本、目录、相对路径和稳定身份 | 文件没被打开，也必须存在于清单中 |
| 打开的文档 | 文本缓冲区、dirty、撤销、编码/换行、光标和标签 | 用户未保存的内容不能被磁盘扫描覆盖 |
| C# 工程上下文 | 源文件集合、框架、语言版本、引用程序集和工程配置 | 目录树本身不能提供可靠的跨文件语义 |

推荐关系：

```text
当前项目 / assetRoot
        ↓
ScriptWorkspace：完整目录清单、变更事件、项目代次
        ├─ Explorer：文件树与快速打开
        ├─ DocumentStore：打开文件、保存与冲突处理
        ├─ Search / SymbolIndex：全项目文本搜索与基础索引
        └─ C# ProjectContext：工程清单与程序集引用
                  ├─ LanguageService：补全、跳转、诊断
                  └─ BuildService：产物与错误报告
                                ↓
                         Runtime 安全点应用
```

上面的服务名为拟议职责，不表示仓库已经存在同名类。初期可以是小规模实现；重点是一个权威脚本清单和明确的文档状态，不是一次重构整个编辑器。

### 4.1 目录树技术路线

| 路线 | 优点 | 局限 | 判断 |
|---|---|---|---|
| `QTreeView + QFileSystemModel` | Qt 原生；目录填充在独立线程进行，自带文件缓存及监听 [R2] | 懒加载结果不等于全工程脚本清单；筛选目录与完整索引仍要单独协调 | 适合快速做可浏览的首版，但不能把它直接当语言服务的完整清单 |
| 共享脚本目录快照 + 自有树模型 | Explorer、搜索、索引和工程生成共享同一份文件集合；方便增量更新和项目切换 | 需要管理扫描任务、树差量和监听生命周期 | **推荐的长期结构**；可用轻量快照先实现 |
| 复制 ProjectPanel 的整套 UI | 看起来接入快 | 复制资产网格、筛选、同步遍历和监听逻辑，形成两套状态 | 不建议整块复制；应提取可共享的数据与操作能力 |

现有 `ProjectTreeNode`、目录遍历、路径/GUID 映射和资产操作可作为基础，但先修正其过滤规则。Project 树当前会跳过 `Configs` 和点号目录；符号索引又有另一套跳过名单；程序集源文件收集则递归纳入全部 `.cs`。三者目前不一致。[E3、E4、E8]

因此推荐：**先定义全 Assets 的脚本清单契约，再把 Explorer 和符号索引接到清单上，最后让工程生成复用它。**

### 4.2 增量刷新与文件变化

工作区服务应同时处理两类事件：编辑器内部资产操作完成事件，以及外部文件系统变化。监听目录用于发现新增/删除；对需要检测内容变化的脚本建立文件监听，并用内容指纹去重。仅监听已打开文件不够，目录监听也不能被假定能可靠报告所有既有文件内容变化。

建议采用 150—300ms 的事件合并窗口，只更新受影响目录/文件。扫描在后台完成，UI 线程应用差量；不在每次按键时递归扫整个 Assets。该窗口是建议参数，需要后续验证。

| 变化 | 目录树 | 已打开文档/项目上下文 |
|---|---|---|
| 外部新增 `.cs` | 自动出现，必要时增加祖先目录 | 加入工程清单与索引，无需先打开文件 |
| 外部修改未打开文件 | 位置不变 | 更新内容指纹、索引和语言服务状态 |
| 外部修改已打开且干净文件 | 位置不变 | 安全刷新，并尽量保留光标、滚动位置 |
| 外部修改 dirty 文件 | 标记冲突 | 保留内存文本，提供比较、重载或覆盖选择 |
| 重命名/移动文件或目录 | 更新节点，保留展开状态 | 内部操作按 GUID/旧新路径迁移标签；外部变更无法可靠匹配身份时按删除+新增处理并提示 |
| 删除已打开文件 | 移除树节点或标记缺失 | 保留未保存内容，提供另存；不要无提示关掉标签 |
| 外部编辑器原子替换保存 | 刷新原节点 | 检查监听是否脱落并重新注册 |
| 切换项目 | 替换整棵树 | 先解决旧项目 dirty 文档，再切换路径、监听、索引和工程上下文 |

Qt 官方说明文件被移走或删除后，`QFileSystemWatcher` 会停止监听；监听注册也可能失败。[R3] 现有 ProjectPanel 有最多 2048 个子目录的监听收集上限及失败日志；不能直接承诺它已覆盖任意规模项目。[E4]

补救策略：监听注册失败时显示降级状态，保留手动刷新；面板重新显示/窗口重新获得焦点时校验目录快照，必要时使用低频指纹扫描兜底。扫描任务携带 `workspaceGeneration`，旧项目的异步结果不得回填新项目。

### 4.3 文件操作复用与文档身份

新建、移动、重命名、删除尽量经过现有 `AssetController` 和 `AssetFileOperations`，继承 `.meta` 与资产 GUID 的处理规则。不要让脚本树直接使用另一套裸文件删除/移动实现。[E5]

路径需要统一绝对路径、分隔符和 Windows 文件系统身份判定；不能只靠文件名去重。现有 `CSharpSymbolIndex::normalizePath` 主要做绝对路径和分隔符规范化，后续还需处理别名和大小写指向同一文件的情况。[E3]

当前文件高亮、目录展开、标签顺序属于工作区状态；撤销栈和未保存文本属于文档状态。普通树刷新不能通过重建编辑器控件来实现。

## 5. 像 VS Code 打开 Unity 项目，还需要工程上下文

自动目录树解决的是“看见和管理所有文件”。跨文件类型识别、成员补全、方法参数、引用查找，则需要 C# 工程及语言服务。

VS Code 的 Unity 集成依赖 Unity 扩展及对应编辑器包，并提供 IntelliSense、导航等能力。[R1] 对 Dodoe 的借鉴应是“项目自动接入 + 文件工作区 + C# 上下文”，而不是假定嵌入一个代码控件就获得全部能力。

### 5.1 当前工程基础可以复用

Windows 平台代码已经生成 `<项目名>.generated.csproj`，设置 `net10.0`、C# 12、源码列表及 `GreenCake.dll` 引用。以仓库中的 Showcase 示例工程为例，其源文件位于对应项目的 Assets 下。[E8]

但目前工程文件生成与程序集构建放在同一个入口。应把“发现源文件并生成/更新工程描述”独立出来，让 ScriptPanel 打开后即可准备项目上下文。

此外，仓库根 `DodoeScripts.sln` 当前只列出 OnlyOne。不能固定让语言服务打开这个解决方案，否则切换到其他项目时，可能显示的是当前 Assets，语义分析却针对另一份工程。[E9]

建议：

- 以当前工作区源文件清单生成对应项目工程；源文件增删、引用或配置变化时更新，纯文本改动无需反复改写工程文件。
- 使用项目对应的 `.csproj`，或自动生成只包含该项目的工作区 `.sln`；不要把开发仓库中的所有测试项目默认混入用户项目。
- 语言版本、目标框架、宏定义、可空设置、引用程序集、生成源码必须与实际运行目标一致。
- Assets 外的 `GreenCake.dll` 是引用上下文，不应被伪装成 Assets 下的用户源文件；可在“依赖/引用”辅助节点显示。
- 文件夹叫 `Editor` 不代表已经拥有 Unity 的编辑器专用程序集语义。当前源文件收集没有这类分组，若以后支持，需要独立定义程序集边界。

### 5.2 语言服务接入建议

首期目录树不依赖 LSP，先让工作区可用。后续为当前项目启动独立 C# 语言服务：

- 向服务器同步 `didOpen / didChange / didSave / didClose`，让补全和诊断看到未保存文本。
- 提供 completion、signatureHelp、hover、definition、documentSymbol 和 diagnostics；rename/references 可逐步补齐。
- 文档带版本号；迟到结果必须与当前版本匹配，不能覆盖新诊断或替换错误位置。
- 正确协商位置编码并转换行列，覆盖中文和 emoji；跨文件修改先校验版本，再形成可撤销操作。[R7]

`csharp-ls` 可作为候选，其项目说明基于 Roslyn，并采用 MIT 许可；具体版本对本仓库 `net10.0 + C# 12 + 生成工程 + GreenCake.dll` 的兼容性，仍需专项验证。[R8] 不把任何候选写成已经验证可直接嵌入的结果。

现有 `CSharpSymbolIndex` 可以作为启动期间/语言服务不可用时的降级，但应明确是词条和启发式导航，不能等同于完整语义补全。

## 6. 配套编辑体验

这部分与工作区建设并行推进，不应替代 Assets 目录树这个首要交付。

### 6.1 字号与常用编辑

- 工具栏/设置中提供字号，编辑器获得焦点时支持 Ctrl+滚轮；增大、减小、重置快捷键作为本产品可配置命令，不假称与 VS Code 的默认按键完全相同。
- 延续现有 11pt 作为迁移默认值，建议允许 8—32pt；Qt 字号单位与网页像素不同，设置项明确为 pt。
- 改字号时同步更新行号栏宽度、行高、Tab 距离和补全弹窗；保持光标、选区和滚动锚点。Qt 已有 `zoomIn/zoomOut` 基础能力。[R4]
- 接入现有 `EditorConfig` 的用户层持久化能力，不只修改一次控件字体；新标签和主题切换后仍遵循用户设置。[E6]
- 补齐行注释、移动/复制行、跳到行、Ctrl+P、工作区文本搜索；多光标、折叠、格式化等作为明确的后续范围。
- 文件浏览/搜索不能只覆盖已打开标签；未保存文档参与搜索时，优先使用内存内容，并标记其未保存状态。

### 6.2 括号与引号自动闭合

用户输入 `(`、`[`、`{`、双引号和单引号时，自动插入对应右侧符号，光标留在中间。此功能属于编辑器输入规则，不依赖语义服务器，也不是当前词条弹窗的同一项功能。

VS Code 的语言配置区分 `autoClosingPairs`、`surroundingPairs`，并可通过 `notIn` 控制字符串/注释中的行为。[R5] Dodoe 应定义并验证自己的 C# 规则：

| 情况 | 目标行为 |
|---|---|
| 普通代码里输入左括号 | 补右括号，光标置中 |
| 输入编辑器刚自动生成的右括号/引号 | 越过对应字符，不重复插入；跟踪自动生成的配对范围 |
| 空配对中按 Backspace | 成对删除，作为一次撤销操作 |
| 选中文本后输入配对符号 | 包裹选区，不删除原文本 |
| `{}` 中按 Enter | 展成三行，光标停在内层缩进位置 |
| 注释、普通字符串、字符字面量 | 根据词法上下文处理；不能盲目补括号或双引号 |
| 转义、逐字字符串、插值字符串、原始字符串 | 分别识别 `\"`、`@"..."`、`$"..."`、`"""..."""` 等上下文；不确定时保守不补 |
| 输入法组合输入、粘贴 | 不把预编辑状态或整段粘贴拆成自动补对事件 |

当前高亮器已有部分字符串/注释状态，可作为词法状态抽取基础，但没有完整覆盖原始字符串与插值表达式。[E2] 输入规则应与高亮共用可查询的状态，避免两套解析各自漂移。

同时修正现有 Enter 和多行缩进的撤销分组：当前 Enter 基于整行末尾判断 `{`，多行缩进按每行分别开启编辑块；需重点验证 `{|}`、行中换行、选区缩进和一次撤销的行为。[E2]

## 7. 脚本修改后如何生效

### 7.1 四件事分别表达

1. **编辑诊断**：分析内存文本，提示语法和类型问题。
2. **保存**：把文档内容写入磁盘。
3. **编译**：用一致的项目输入产生程序集。
4. **应用**：运行时加载新程序集，重建必要状态。

目录树发现脚本，不代表它已经进入当前运行版本；保存成功也不代表已经生效。状态栏应表达这几个阶段。

### 7.2 手动还是自动：推荐分阶段的混合方式

**最终默认建议：保存后后台编译，编辑态安全点应用，运行/暂停期间默认延后到停止后应用；始终保留手动入口。** 不建议每次按键都启动一次完整构建，也不建议仅靠用户记住手动刷新。

但第一版先做好手动入口和可见诊断，待失败恢复与状态迁移可靠后，再开启保存后自动模式。

| 时机 | 建议行为 |
|---|---|
| 仅输入、尚未保存 | 语义诊断更新，不生成并替换运行程序集 |
| 保存或 Save All 完成 | 自动模式下按项目合并事件，约 750ms 后发起一次后台任务；手动模式只标记待处理 |
| 外部工具保存或新增/删除脚本 | 经完整目录清单校验后，进入同一调度入口，不能只看当前标签 |
| 点击“编译脚本” | 明确处理未保存文件；可选择保存全部并继续；保存失败则中止。必要时提供强制重新生成选项 |
| 编辑态产生新版本 | 校验成功后，在运行时安全点应用；有不兼容状态或应用失败则保留旧版本/进入可恢复状态 |
| Playing/Paused 产生新版本 | 可以后台生成产物，但标记“待应用”，默认保持当前运行版本 |
| 停止运行 | 与场景保留/丢弃流程协调后，再应用最新有效版本 |
| 点击 Play | 检查未保存文档及源码/产物/已应用版本；需要时保存、更新并应用，成功后进入 Play；失败不静默运行旧代码 |

“保存触发”与“Play 前检查”应是独立设置。选择手动模式只关闭保存触发；Play 前仍需发现过期状态，并明确提供更新后运行、显式使用旧版本或取消，而不是偷偷忽略。

750ms 等参数属于建议起点，不是已经测得的最佳数值。

### 7.3 当前运行时已有基础，但不能直接接到每次保存

现有非 Shipping 初始化流程会按源文件指纹判断是否需要生成程序集；指纹主要包含路径、文件大小、修改时间。显式重载流程为：[E10、E11]

```text
检查源码变化 → 构建程序集 → 字段快照 → 清理运行状态
→ 卸载旧程序集 → 加载新程序集 → 注册/重建类型
→ 恢复字段 → 提交源码指纹
```

这里是**程序集卸载与重新加载**，不能直接宣称等同于无状态损失的 .NET Hot Reload。当前 Qt 的 Play 切换只改变 World 状态，并未在该路径中检查脚本更新；已找到的手动重载调用在调试 ImGui 面板。[E11、E13]

自动化前必须处理以下问题：

- **保存结果不可靠**：`savePage` 不返回成功与否，`saveAll` 最后无条件返回 true；关闭标签/关闭所有标签的“保存”分支未检查结果。要先让失败保留 dirty 文档并阻止后续动作。[E1]
- **同步等待**：Windows 进程入口使用无限等待。直接从 UI 保存回调调用可能卡住界面。改成异步进程，持续采集 stdout/stderr、退出码与错误位置；Qt `QProcess` 提供相应信号。[E8、R6]
- **加载失败恢复缺失**：重载在清空状态、卸载旧程序集后才加载新版本；加载失败直接返回，未见旧版本恢复流程。生成成功不代表应用一定成功。[E11]
- **字段恢复需专项验证**：托管快照按旧 ObjectRegistry handle 保存，Reset 会清空注册表，新实例使用递增的新 handle，Restore 又按旧 handle 查找；此外 native 侧将字段 JSON `dump()` 保存为字符串，再构造恢复 JSON，可能改变数字/对象等字段的 JSON 类型。这些是源码可见的高风险路径，不应据函数名推断恢复已可靠。[E12]
- **引用与零脚本场景**：当前指纹未覆盖全部引用/工程配置，零脚本返回也有独立分支。最后一个 `.cs` 删除时要明确清空/更新脚本程序集，不能留下仍执行旧类的版本。[E8、E10]

建议将构建产物写到版本化的临时目录，保留上一个可用版本；把“生成产物”和“运行时应用”拆成两个阶段。旧版本恢复不是仅备份一个 DLL，还要覆盖依赖、实例身份、字段映射及失败后的状态重建。

后台仅做文件处理、进程和诊断；运行时对象重建仍由安全点执行，不要把现有整个重载函数简单放进工作线程。`AssemblyLoadContext` 的卸载是协作式的，线程调用栈、静态引用、GCHandle 等都可能阻止彻底卸载。[R9]

### 7.4 调度与状态要求

- 同一项目最多一个任务在执行；期间再次保存，只保留一个指向最新输入的待处理请求。
- 区分 `sourceRevision`、`builtRevision`、`appliedRevision`。文件已保存、产物已更新、运行时已更新是不同状态。
- 输入包含源码集合/内容、工程配置、引用版本；仅依赖文件时间戳不足以保证正确性。
- 构建期间输入变化，旧结果不得标成最新；使用不可变输入快照，或在结束时重新校验版本并丢弃过期结果。
- 项目切换、退出、任务取消应清理子进程和回调；旧项目任务不得污染新项目诊断或状态。
- “没有变化”作为正常结果处理，与失败分开；错误保留到 Problems，可跳到相应文件行列。

## 8. 是否更换编辑器控件

**自动 Assets 目录树不需要先替换当前 Qt 代码控件。** 目录、文档、工程上下文应独立于编辑器内核建设。

| 方案 | 适合的范围 | 本次建议 |
|---|---|---|
| 保留 `QPlainTextEdit`，补工作区、输入规则和 LSP | 当前 Qt 集成；先解决目录与高频编辑问题 | **主路线**，最能复用现有标签、高亮和查找能力 |
| Monaco + Qt WebEngine + C# 语言服务桥接 | 多光标、折叠、编辑行为等大量能力都要向 VS Code 靠拢 | 单独做验证，不作为目录树首版前置条件 |
| 打开外部 VS Code | 暂时需要成熟 IDE、重构和调试 | 可保留为辅助入口，不能代替内置 ScriptPanel 的完整工作区 |

Monaco 来自 VS Code 的编辑器源码，但官方 FAQ 明确普通 VS Code 扩展不能直接在 Monaco 中使用。[R10] 接入它仍需自行实现 Explorer、项目工程、C# 服务、文件桥接与运行时应用，不能把“换控件”理解为“嵌入完整 VS Code”。现有 Editor 依赖声明中未接入 Qt WebEngine。[E14]

## 9. 建议实施顺序与触及位置

| 阶段 | 必须交付 | 主要位置 | 完成判断 |
|---|---|---|---|
| A：完整工作区（最高优先级） | 自动绑定当前项目、全 Assets 递归发现、真实目录树、无标签仍可浏览、外部增删改同步、项目切换隔离 | `ScriptPanel`、`EditorWindow`；提取脚本清单服务/树 ViewModel，复用资产能力 | 不打开任何脚本，进入面板就能看到全部目录与脚本 |
| B：可靠文档与基础编辑 | 保存失败保护、路径/标签身份、快捷打开和搜索、字号、括号/引号闭合、撤销分组 | `CSharpCodeEditor`、`CSharpHighlighter`、文档状态与 `EditorConfig` | 常用编辑行为一致，刷新/切换不丢未保存内容 |
| C：项目理解与手动生效 | 独立工程生成、C# 语言服务、Problems、异步手动构建、应用结果可见 | 平台工程生成逻辑、新语言/构建服务、现有 ScriptEngine/ScriptSystem | 任意 Assets 脚本可被工程识别，错误可定位，失败不破坏有效状态 |
| D：自动化 | 保存后合并任务、版本化产物、停止后应用、Play 前检查、可靠恢复 | 构建调度、RuntimeBackend/PlayModeController、安全点流程 | 自动流程通过失败/并发/状态迁移验收后再设为默认 |

`ScriptWindowController` 当前负责 C# 自定义编辑器窗口，不是脚本文件工作区控制器；不要仅因名字相近就将目录扫描、文档管理全部塞入该类。

不建议同时维护两套文件清单、两套资产移动规则和两套工程排除规则。优先抽取可共享的基础能力，而不是复制 ProjectPanel。

## 10. 验收清单

以下是后续实现的验收要求，不表示本次已执行这些场景。

### A. 工作区与目录树

- 打开项目后，直接显示 ScriptPanel，不预先打开 `.cs`，即可看到 Assets 根目录及完整层级。
- 根目录脚本、非 Scripts 目录脚本、深层脚本、中文路径、同名文件均正确显示；空目录保留。
- 默认不会因 `Assets/Configs`、`Assets/Build` 等名称漏掉 `.cs`；显式忽略规则能解释被排除内容。
- 外部新建、删除、重命名、移动脚本和目录后自动同步；新文件没有 `.meta` 或尚未导入时也可见。
- 关闭最后一个标签后目录树仍在；通过菜单/工作区按钮重新显示面板也能自动恢复当前项目。
- 从 Project 双击脚本、从脚本树打开、通过 Ctrl+P 打开同一路径，最终共用一个文档。
- 目录刷新保留展开、选中、滚动和标签；目录重命名正确迁移子文件身份。
- 由项目 A 切到 B，旧扫描、监听、补全和诊断不会回填 B；取消切换时 A 的文档完整保留。
- 大量文件/深目录下仍可响应输入；监听数量不足或目录不可读时有明确降级提示。规模和耗时阈值由实际样本确定。

### B. 编辑与工程上下文

- Save All 中任意文件保存失败，不能把整体当作成功；关闭、切换项目和后续任务都不丢失 dirty 文档。
- 外部修改与未保存缓冲区冲突时不覆盖内存文本；原子替换后仍能继续收到变化。
- 同一个符号跨文件引用、局部变量同名、未保存成员、引擎 API 引用能得到正确结果；测试当前实际项目而非固定 OnlyOne。
- 字号跨标签与重启保留；闭合、越过、成对删除、选区包裹、Enter、撤销和输入法场景符合定义。
- 工作区搜索覆盖未打开文件；打开文件的未保存内容与磁盘版本有明确优先关系。

### C. 生效与失败恢复

- 一次保存、多文件 Save All、连续快速保存都不会产生互相覆盖的并行任务。
- 语法错误、引用缺失、进程失败、取消、程序集加载失败分别有准确状态，旧有效版本不会被误标为新版本。
- Playing/Paused 保存后默认不立即替换运行状态；停止后只应用最新有效产物。
- 新增/删除最后一个脚本、引用程序集变化、项目切换中的迟到结果都能正确处理。
- 重载后的字段值、实体/组件身份、系统实例、静态订阅及卸载状态得到验证；类型变更有明确策略。
- 点击 Play 时源码、产物与应用版本一致；使用旧代码必须是明确选择。
